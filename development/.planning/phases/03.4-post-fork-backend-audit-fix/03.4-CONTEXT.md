# Phase 03.4: Post-Fork Backend Audit & Fix - Context

**Gathered:** 2026-03-24
**Status:** Ready for planning

<domain>
## Phase Boundary

After the accounts fork (Phase 03.3), the entire university_erp backend is fully re-tested across all modules — every doctype accessible in Frappe Desk, every field linked to the correct parent schema, every report running with valid source fields, every workflow functional, all cross-app connections verified — ensuring complete backend stability before any frontend portal work begins. Also seeds comprehensive demo data and creates all missing workflows across the app.

</domain>

<decisions>
## Implementation Decisions

### Demo Data
- **D-01:** Large-scale data: 500+ students across multiple programs, 50+ faculty, multiple departments, full academic year with terms
- **D-02:** Wipe existing seed data before re-seeding (clean slate approach)
- **D-03:** Financial transactions MUST go through the new university_finance module — fee records that post GL entries via the forked module to validate the fork works end-to-end with real data
- **D-04:** Script must be idempotent (check-before-create pattern, safe to re-run after fixes)
- **D-05:** Script approach: Claude decides whether to extend existing `seed_demo_data.py` or create new dedicated script based on what makes sense

### Workflow Testing & Creation
- **D-06:** Full end-to-end testing in Frappe Desk — actually submit documents through each workflow stage (Draft→Submit→Approve) via bench console, verify state transitions, GL postings, status updates
- **D-07:** Discover ALL needed workflows across the entire app — not just the 4 listed (fee collection, leave approval, admission, grade submission) but also hostel fees, room allocation, grievance workflow, transport, library, placement, and any others identified during research
- **D-08:** Create any missing workflows that should exist but don't (hostel fee payment, room allocation approval, grievance resolution, etc.)
- **D-09:** Test ALL workflows — both existing and newly created
- **D-10:** Fix failures immediately — no documenting and deferring. If a workflow fails, find and fix the root cause in this phase

### Report Failure Handling
- **D-11:** Fix university_erp and university_finance reports only. ERPNext/HRMS reports that fail due to missing Company setup are expected failures in a university context — leave them as-is
- **D-12:** Disable original ERPNext Accounts report versions via permissions — restrict so only System Manager can see them. University users see university_finance versions (Fee Receivable, Vendor Payable, Student Ledger, etc.)

### Full App Schema Audits
- **D-13:** Expand the phase to cover the complete university_erp app, not only finance/hostel/transport slices. Audit every module, doctype, and report in university_erp before applying fixes.
- **D-14:** Schema-first rule: before auditing or fixing any field or report, inspect the parent doctype JSON/schema on disk and match the exact target doctype, fieldtype, and join/filter field names.
- **D-15:** Report validation must verify the report's actual source doctype schema, filter field names, and join fields so rendered data matches the available schema and does not fail on missing fields.

### Claude's Discretion
- Exact demo data distribution (how many students per program, department sizes)
- Which specific workflows to create beyond the obvious ones (based on research of the app modules)
- How to structure the seed script (extend vs. new file)
- Order of audit operations (reports first vs. doctypes first vs. workflows first)

</decisions>

## Addendum (2026-05-15) — Refresh after Phase 03.3.1 (Education-app fork)

**Trigger:** Phase 03.3.1 completed waves 1–4 between original 03.4 planning (2026-03-24) and now, forking 71 Education doctypes into university_erp modules. Re-running `/gsd-discuss-phase 03.4` to lock new decisions for plans 02–05 before they execute. Decisions D-01..D-15 above remain valid; Plan 03.4-01 (executed 2026-04-28) is unaffected. Addendum decisions D-16..D-22 only constrain plans 02–05.

### Δ1 — Module ownership shift after Education fork
- **D-16:** Plans 03/04/05 audit scope = all 17 university_erp modules + university_finance. The 7 Education-owned ARCHIVE doctypes (Quiz/Article/Student Report Gen Tool) are skipped per D-19. ERPNext/HRMS remain out-of-scope per D-11.
- **D-17:** Cross-app Link validation in plan 04 — for every Link/Dynamic Link/Table field, verify that (a) the target DocType exists in DB AND (b) its `module` field is one of the university_erp modules. Failures of either condition block the plan; the second condition catches links that resolve at runtime but point at deprecated modules (Education leftovers).

### Δ2 — Workflow inventory drift (16 workflows already exist, not 3)
- **D-18:** Plan 02 must re-audit existing workflows FIRST before creating any. Algorithm: query `tabWorkflow` for active workflows → cross-reference against the set of submittable doctypes that have status fields → only generate Workflow records for the actual delta. Each create call wraps in `if not frappe.db.exists("Workflow", workflow_name)` for idempotency.
- **D-18a:** Plan 02 E2E test loop is per-workflow: create test document → walk every state transition via `frappe.model.workflow.apply_workflow` → verify final state matches expected → delete test document. No structural-only checks; transition execution is what matters.

### Δ3 — overrides/ directory deleted (Phase 03.3.1-05)
- **D-19a:** `university_erp/overrides/` no longer exists; all controllers live in their forked module locations. Audit scripts that walked `overrides/` are obsolete; schema audit (plan 04) walks `university_erp/<module>/doctype/<dt>/<dt>.py` paths directly. No script-rewrite work needed since plans 03/04/05 don't reference `overrides/`.

### Δ4 — ARCHIVE_DOCTYPES (7 items still module='Education')
- **D-19:** All 7 ARCHIVE_DOCTYPES (Article, Options, Question, Quiz, Quiz Activity, Quiz Result, Student Report Generation Tool) confirmed to have ZERO Link/Table field references from any university_erp doctype. Audit (precise Link target check) ran 2026-05-15 returned 0 hits. Their on-disk forks at `university_academics/_archived/` and `university_student_info/_archived/` are kept for archival but plans 03/04/05 skip them entirely. They will be dropped (DB tables + `_archived/` dirs) when Education app is uninstalled in a future session.

### Δ5 — Workspace card-rendering check (newly understood failure mode)
- **D-20:** Plan 03 desk-accessibility audit MUST include a workspace consistency check. For every public Workspace, parse `Workspace.content` JSON and extract all `card_name` values; cross-reference against `tabWorkspace Link` rows where `type='Card Break'` for that workspace; FAIL if any Card Break in `links` is missing from `content` (the failure mode that hid 39 forked academics doctypes for hours this session). Add this as a new Step in plan 03's audit_desk_ui.py invocation, persisted as `WORKSPACE_AUDIT.md`.

### Δ6 — Education app still installed (uninstall deferred from 03.3.1)
- **D-21:** All audit scripts in plans 03/04/05 filter at the source: `WHERE module != 'Education'` for any DocType/Report query. Education-owned items are completely invisible to these audits. When Education is finally uninstalled (separate user-driven session, currently held open as 03.3.1-HUMAN-UAT item 1), Education-module rows disappear naturally without changing audit outputs.

### Carry-forward and ARCHIVE cleanup decision
- **D-22:** No new Plan 03.4-06 created for ARCHIVE cleanup. The `_archived/` directories and orphan DB tables get cleaned up alongside the Education app uninstall, NOT in this phase.

### What this addendum does NOT change
- Plan 03.4-01 (executed) is unaffected — comprehensive demo data seed already ran.
- D-01..D-15 above remain authoritative for the unchanged decisions.
