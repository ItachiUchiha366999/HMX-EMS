<domain>
## Phase Boundary

After the Education-app fork (Phase 03.3.1) moved 71 doctypes from the Education app into seven university_erp modules (university_academics, university_student_info, university_admissions, university_hostel, faculty_management, university_finance, with workspace and hooks wiring), the entire university_erp backend must be re-validated. Every doctype must be reachable in Frappe Desk under the correct workspace, every Link/Table field must resolve to a DocType in a current university_erp module, every report must execute against the new schema locations, every workflow must operate end-to-end on the post-fork doctypes, and demo data must populate the new module ownership cleanly.

This phase is the quality gate before any frontend portal work. It is read-mostly for the system as a whole, write-mostly for the fixes that follow the audits. ERPNext/HRMS remain vendored and out-of-scope. Education is filtered out of audits at the source — the app stays installed during this phase but its 7 leftover doctypes (Quiz suite + Article + Student Report Generation Tool) are invisible to audit queries.

</domain>

<decisions>
## Implementation Decisions (all locked)

### Audit scope
- **D-01:** Audit scope = all 17 university_erp modules + university_finance. The 7 Education-owned ARCHIVE doctypes (Quiz, Question, Quiz Activity, Quiz Result, Article, Options, Student Report Generation Tool) are skipped entirely — verified 2026-05-15 to have zero Link/Table field references from any university_erp doctype. ERPNext/HRMS remain out-of-scope as vendored apps.
- **D-02:** All audit scripts filter at the source with `WHERE module != 'Education'` for any DocType/Report query. Education-installed-but-deprecated state is treated as if Education weren't there. When Education is finally uninstalled (separate user-driven session, currently held open as 03.3.1-HUMAN-UAT item 1), audit outputs do not change.

### Cross-app validation
- **D-03:** Cross-app Link validation (plan 04) — for every Link/Dynamic Link/Table field, audit verifies (a) target DocType exists in DB AND (b) its `module` field is one of the university_erp modules. Both conditions are blocking. The second condition catches links that resolve at runtime but point at deprecated/wrong modules.

### Workflow strategy
- **D-04:** Plan 02 must re-audit existing workflows BEFORE creating any. Algorithm: query `tabWorkflow` → cross-reference against submittable doctypes that have a status field → only generate Workflow records for the actual delta. Each create call wraps in `if not frappe.db.exists("Workflow", workflow_name)` for idempotency. As of 2026-05-15 the DB has 16 active workflows (Certificate Request, Course Registration, Fee Refund, Generated Question Paper, Grievance Resolution, Hostel Allocation, Hostel Maintenance Request, Journal Entry, Lab Equipment Booking, Leave Application, Merit List, Payment Entry, Research Grant, Revaluation Request, Teaching Assignment, Transport Allocation).
- **D-05:** Workflow E2E test loop is per-workflow: create test document → walk every state transition via `frappe.model.workflow.apply_workflow` → verify final state matches expected → delete test document. No structural-only checks; transition execution is what matters. Failures fix immediately.

### Workspace & desk
- **D-06:** Plan 03 desk-accessibility audit MUST include a Workspace consistency check. For every public Workspace, parse `Workspace.content` JSON and extract all `card_name` values; cross-reference against `tabWorkspace Link` rows where `type='Card Break'` for that workspace; FAIL if any Card Break in `links` is missing from `content` (the failure mode that hid 39 forked academics doctypes during phase 03.3.1 workspace fix-up). Output persists as a `WORKSPACE_AUDIT` section of the consolidated `AUDIT_REPORT.md`.

### Cleanup & deferred
- **D-07:** ARCHIVE_DOCTYPES (the 7 deprecated items at `university_academics/_archived/` and `university_student_info/_archived/`) and their orphan DB tables get cleaned up alongside the Education app uninstall, NOT in this phase. The `_archived/` directories stay on disk for archival; their DB tables stay too. They are simply skipped by audits per D-01.
- **D-07a:** `overrides/` directory no longer exists (deleted in Phase 03.3.1-05). Schema audit (plan 04) walks `university_erp/<module>/doctype/<dt>/<dt>.py` paths directly. No script-rewrite work needed since plans 03/04/05 don't reference `overrides/`.

### Demo data (plan 01)
- **D-08:** Plan 01 must be RE-EXECUTED. The April 2026 demo data (510 students, 800 GL entries) was seeded against pre-3.3.1 schema where Student/Course/Program/Fees lived in the Education app. Post-3.3.1 those doctypes belong to university_erp modules. Re-run uses wipe-and-reseed: drop existing demo data → re-seed against the new module ownership. The Phase 03.3.1 DB backup at `development/backups/pre-03.3.1-20260514-181929/` is the rollback safety net.
- **D-09:** Demo data volumes from prior CONTEXT remain: 500+ students across multiple programs, 50+ faculty, multiple departments, full academic year with terms. Financial transactions still post via university_finance to validate the fork. Script must be idempotent (check-before-create) and self-contained (no manual setup steps).

### Reports & permissions
- **D-10:** Report-source-schema audit (plan 05) verifies for every report: source DocType field names exist; filter field names exist; join field names exist on both sides; group-by columns exist. Fixes are immediate. Reports owned by ERPNext/HRMS that fail due to missing Company setup remain out-of-scope (carried from prior D-11).
- **D-11:** ERPNext Accounts original reports stay restricted to System Manager only (carried from prior D-12). University users see the university_finance versions (Fee Receivable, Vendor Payable, Student Ledger Summary, etc.). The restriction script `restrict_erpnext_reports.py` re-runs if needed.

### Output discipline
- **D-12:** Each plan produces ONE consolidated `AUDIT_REPORT.md` (not a fan-out of multiple files). Sections within the report cover the plan's distinct audit areas. Centralized review.

### Plan structure
- **D-13:** 5-plan structure mirrors original layout, refreshed against the new CONTEXT:
  - Plan 01 — Demo data validate & re-seed (post-3.3.1 schema)
  - Plan 02 — Workflows audit-then-create-gap (per D-04, D-05)
  - Plan 03 — Reports + permissions + desk + workspace audit (per D-06, D-10, D-11)
  - Plan 04 — Schema-link audit (per D-03)
  - Plan 05 — Report-source-schema audit (per D-10)
